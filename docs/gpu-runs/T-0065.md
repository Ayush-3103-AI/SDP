# 📦 DATA SITTING — T-0065 Download CAXTON and run the data sitting  (issue #65)
Written against: the ADR-0009 re-plan (2026-10-27) · Needs GPU: **no** · Needs disk: ~150 GB for the full image set
[estimate: 1.27 M images × ~120 KB], ~2 GB for our crops · Est. time: Part 1 ≈ 1 h of work + download time; Part 2 ≈ 2–4 h
Batch: do the CPU runs (T-0023, T-0052, T-0037/38, T-0043/44) in the same sitting if you like; they don't touch this data.

**Why this matters:** CAXTON (Cambridge, Brion & Pattinson 2022) is the only dataset whose images are labelled with the
printer settings that caused them. Our cause model, conformal sets and early warnings are all trained and tested on it.
Everything stays on **your** laptop: never commit images, crops or the raw CSVs.

## Part 1 — start now (no code from us needed)
1. **Find the images.** The Apollo record https://www.repository.cam.ac.uk/handle/1810/339869 (DOI 10.17863/CAM.84082) lists
   five label CSVs. Its file list has a "Show more" button. Click it and look for image archives (zip/tar, possibly one per
   print). Also check the related records linked from it: https://doi.org/10.17863/CAM.100129 and
   https://www.repository.cam.ac.uk/handle/1810/341089, and the README of https://github.com/cam-cambridge/caxton.
   Expected: a download link for the images, `caxton_dataset/print<N>/image-<M>.jpg` once extracted.
2. **Download the label CSV** `caxton_dataset_filtered.csv` (120 MB) into `D:\caxton\`. If you find the images, download
   them into `D:\caxton\` so that `D:\caxton\caxton_dataset\print0\...` exists. If they come per print and disk is
   short, download prints 0–182 only (183–191 are excluded anyway).
3. **Record the provenance** in `docs/data/CAXTON.md` (new file, in the repo):

## Part 2 — after Claude marks steps 30–34 DONE (the five data scripts)
Claude updates this section and comments on #65 when the scripts are ready. The planned commands (08-pseudocode P8) are:
1. `uv run python scripts/adapt_caxton.py --csv D:\caxton\caxton_dataset_filtered.csv --root D:\caxton --out data --per-print 500 --seed 0`
   Expected: printed counts (prints, images in, excluded by reason, kept by cause); `data\trials.csv`, `data\images.csv`,
   `data\adapt_counts.json` (the audit reads it). ~2 min. If the images come per print, add
   `--list-needed needed.txt` to get the exact list of images to fetch.
2. `uv run python scripts/build_crops.py --images data\images.csv --root D:\caxton --out data\crops --workers 4`
   Expected: ~90 k crops in `data\crops\`, `data\crops.csv`; a missing count (should be ~0). 20–40 min. Safe to re-run.
3. `uv run python scripts/audit_data.py` → `reports\data_audit.md`. First line `K1′: PASS` or `K1′: FAIL (...)`. 1 min.
   It reads the licence line of `docs/data/CAXTON.md` (Part 1 step 3), so fill that in first.
4. `uv run python scripts/derive_window.py` → `reports\l3_window.md`. 1 min.
5. `uv run python scripts/make_splits.py` → `data\splits\logo.json`. 1 min. Run it **once**: it refuses to overwrite.
   The splits are by print, so they don't depend on which causes the audit proposes to drop.

## If it fails
- `adapt_caxton.py` exits 2 with "missing columns": paste the message into #65; don't edit the CSV. Claude fixes the mapping.
- `adapt_caxton.py` exits 2 with "class columns with values outside {0, 1, 2}": paste the message into #65.
- `build_crops.py` reports almost every image as `missing`: the CSV's `img_path` is not relative to `--root`. Paste the
  first `img_path` and your folder layout (`dir D:\caxton`) into #65; don't edit the CSV.
- Crops are slow: `--workers 2` if the laptop overheats; the script resumes where it stopped.
- Out of disk: delete the raw images of prints whose crops are done? **No.** Keep the raw data until the T-0013 run is
  accepted, in case crops must be rebuilt. Free space elsewhere or use an external drive for `D:\caxton`.
- `make_splits.py` says logo.json exists: someone already ran it. `git pull`; don't use --force.
